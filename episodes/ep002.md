# EP.002 — Why is `count++` not thread-safe even with `volatile`?

## Answer

`volatile` guarantees **visibility**: when one thread writes a volatile variable, other threads see that write. It also provides ordering guarantees. What it does **not** guarantee is atomicity.

`count++` looks like one operation, but it is a **read-modify-write** sequence:

1. Read `count`.
2. Add one to the value.
3. Write the result back.

Two threads can both read 41, both calculate 42, and both write 42. Two increments produce only one. That is a **lost update**, and `volatile` cannot prevent it.

### The race

```java
private volatile int count = 0;

public void increment() {
    count++; // still not atomic
}
```

- Thread A reads 41.
- Thread B reads 41 before A writes.
- Both threads write 42.
- One increment disappears.

### The fix

Use an atomic operation so the read, update, and write happen as one indivisible action:

```java
private final AtomicInteger count = new AtomicInteger(0);

public int increment() {
    return count.incrementAndGet();
}
```

`AtomicInteger` uses a compare-and-set loop: it retries if another thread changes the value first. A `synchronized` method or block is another valid fix, especially when several values must be updated together.

### Takeaway

Use `volatile` for a simple shared flag, such as a shutdown signal. Use an atomic or a lock when correctness depends on the previous value.

### Interview follow-ups

- **When is `volatile` enough?** A single variable whose new value does not depend on its old value, such as `volatile boolean running`.
- **Why not synchronize everything?** Unnecessary locking can reduce concurrency and create contention, but correctness comes first.
- **Would `LongAdder` be better?** Often for high-contention counters and metrics, but it is not a drop-in replacement when you need an exact instantaneous total.
