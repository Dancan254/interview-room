## Answer

Your embedded Tomcat uses an **acceptor thread** to pick up incoming connections and hands each one to a **worker thread** from a pool. By default, that pool has **200 threads**. Every request gets its own thread.

Your controller runs on one thread, calls the service, waits on the database, and returns. The other 199 requests do the exact same thing, in parallel. That is the **thread-per-request** model.

### The two failure modes

1. **Pool exhaustion.** If all 200 threads are stuck waiting on a slow database, request 201 has to queue. Queues have timeouts, so clients start getting errors while your CPU sits idle.
2. **Virtual threads.** This is the problem virtual threads solve. They make waiting cheap, so one platform thread can host thousands of suspended requests.

### Takeaway

Concurrency in Spring is a thread pool with a fixed size and a queue. Most production incidents are that queue filling up.

### Code snippet: checking your thread pool config

```yaml
# application.yml
server:
  tomcat:
    threads:
      max: 200          # default
      min-spare: 10
    max-connections: 8192
    accept-count: 100   # queue size before rejections
```

```java
// Or configure programmatically
@Bean
public TomcatProtocolHandlerCustomizer<?> protocolHandlerCustomizer() {
    return protocolHandler -> {
        protocolHandler.setMaxThreads(200);
        protocolHandler.setMinSpareThreads(10);
        protocolHandler.setAcceptCount(100);
    };
}
```
